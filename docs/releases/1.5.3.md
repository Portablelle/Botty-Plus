# Botty service 1.5.3 / native app 1.4.1

The native app header shows its update state, separate from manager connectivity.
Connections adds **Check for updates** and, when a newer native package is trusted,
**Update Botty+**. Confirmation defaults to Cancel. A durable queued response lets
the client release its resources and exit normally; an invalid or lost response
keeps it open without automatically replaying the request.

The manager checks the verified native package on Botty+ `main` asynchronously.
It queues the request on disk, waits for the complete compression/activation
pipeline and other file operations, and prevents new file operations from
starting during publication. Downloads, rTorrent, the manager and the compression
worker stay running. The user reopens the native app after a completion
notification; automatic relaunch and background-service self-updates are not
included.

Installation uses bounded HTTPS downloads, exact title/file identities, SHA-256
verification, staged files, directory fsync, the Portal-compatible native journal
and retained title/metadata backups. An unconfirmed idle worker, native process
table, filesystem capability or recovery state blocks publication. Prepublication
failures release the admission guard only when the original files and nonpending
journal can be verified. Uncertain publication keeps its recovery guard.

Initial activation requires Portal+ to install the updated native client and
manager in a deliberately restarted, idle console session. Builds and host tests
are separate from hardware acceptance: manager permissions, stopped-process
detection, ShadowMount unmount/discovery, registered metadata refresh and real
update/reopen still need PS5 validation. No console deployment was performed for
this change.
